# [유저 애플리케이션 서비스] 유스케이스 명세서

> 본 문서는 유저 서비스의 기능적 요구사항을 정의하고, 각 기능별 비지니스 흐름(정상, 대안, 예외 흐름)의 기준을 제공한다.

## 1. 개요 (Overview)

- **도메인**: 인증(로그인/토큰 재발급/로그아웃), 회원(가입/배송지), 내부 조회 API, 포인트 사가 참여, 아웃박스 메시지 발행 등
- **주요 행위자**: 비인가 사용자, 인가된 사용자, 시스템(Kafka 메시지 컨슈머), 시스템(트랜잭션 이벤트 리스너), 시스템(스케줄러), 다른 마이크로서비스(내부 API 호출자, 예:
  order-service)

## 3. 유스케이스 상세 명세 (UseCase Specifications)

### 3.1. [UC-AUTH-01] 로그인

1. 기본 정보
    - 목적: 이메일/비밀번호로 사용자를 인증하고 액세스 토큰과 리프레시 토큰을 발급한다.
    - 행위자: 비인가 사용자
    - 선행 조건: 유효한 계정이 존재해야 한다.
    - 사후 조건: 리프레시 토큰이 Redis에 저장되고, 액세스 토큰은 응답 바디로, 리프레시 토큰은 HttpOnly 쿠키로 반환된다.

2. 기본 흐름
    1. [행위자]: 이메일과 비밀번호를 포함하여 로그인을 요청한다.
    2. [시스템]: 이메일로 유저를 조회한다.
    3. [시스템]: 입력한 비밀번호가 저장된 암호화 비밀번호와 일치하는지 검증한다.
    4. [시스템]: 인증된 유저 정보를 바탕으로 액세스 토큰과 리프레시 토큰을 발급한다.
    5. [시스템]: 발급된 리프레시 토큰을 유저 식별자를 키로 하여 Redis에 TTL과 함께 저장한다(기존 값이 있으면 대체).
    6. [시스템]: 액세스 토큰은 응답 바디로, 리프레시 토큰은 HttpOnly 쿠키로 반환한다.

3. 대안 흐름
   (기본 흐름 외의 정상 대안 흐름 없음)

4. 예외 흐름
    - [E-1] 존재하지 않는 이메일 (기본 흐름 2번에서 발생)
        1. [시스템]: 해당 이메일의 유저가 없음을 확인한다.
        2. [시스템]: 예외(`USER_NOT_FOUND`)를 반환하고 흐름을 종료한다.
    - [E-2] 비밀번호 불일치 (기본 흐름 3번에서 발생)
        1. [시스템]: 입력한 비밀번호가 저장된 암호화 비밀번호와 일치하지 않음을 확인한다.
        2. [시스템]: 예외(`PASSWORD_NOT_MATCH`)를 반환하고 흐름을 종료한다.

### 3.2. [UC-AUTH-02] 토큰 재발급

1. 기본 정보
    - 목적: 유효한 리프레시 토큰을 제시한 사용자에게 새로운 액세스·리프레시 토큰을 발급(로테이션)한다.
    - 행위자: 비인가 사용자(만료된 액세스 토큰을 가진 사용자)
    - 선행 조건: 쿠키에 리프레시 토큰이 존재해야 한다.

2. 기본 흐름
    1. [행위자]: 쿠키에 담긴 리프레시 토큰으로 재발급을 요청한다.
    2. [시스템]: 토큰의 서명과 만료 여부를 검증하여 유저 식별자를 추출한다.
    3. [시스템]: 추출한 유저 식별자로 Redis에 저장된 리프레시 토큰을 조회한다.
    4. [시스템]: 요청된 토큰 값과 저장된 토큰 값이 일치하는지 검증한다.
    5. [시스템]: 유저 식별자로 유저 정보를 조회한다.
    6. [시스템]: 새로운 액세스 토큰과 리프레시 토큰을 발급한다.
    7. [시스템]: 새 리프레시 토큰으로 Redis 값을 갱신한다.
    8. [시스템]: 새 액세스 토큰은 응답 바디로, 새 리프레시 토큰은 HttpOnly 쿠키로 반환한다.

3. 대안 흐름
   (기본 흐름 외의 정상 대안 흐름 없음)

4. 예외 흐름
    - [E-1] 토큰 만료 (기본 흐름 2번에서 발생)
        1. [시스템]: 리프레시 토큰의 만료 시각이 지났음을 확인한다.
        2. [시스템]: 예외(`REFRESH_TOKEN_EXPIRED`)를 반환하고 흐름을 종료한다.
    - [E-2] 토큰 서명/형식 오류 (기본 흐름 2번에서 발생)
        1. [시스템]: 토큰의 서명이 유효하지 않거나 형식이 손상되었음을 확인한다.
        2. [시스템]: 예외(`REFRESH_TOKEN_INVALID`)를 반환하고 흐름을 종료한다.
    - [E-3] 저장된 토큰 없음 (기본 흐름 3번에서 발생)
        1. [시스템]: 해당 유저의 리프레시 토큰이 Redis에 존재하지 않음(만료 또는 로그아웃됨)을 확인한다.
        2. [시스템]: 예외(`REFRESH_TOKEN_NOT_FOUND`)를 반환하고 흐름을 종료한다.
    - [E-4] 토큰 불일치 (기본 흐름 4번에서 발생, 탈취 의심 시나리오)
        1. [시스템]: 요청된 토큰 값이 저장된 토큰 값과 다름을 확인한다.
        2. [시스템]: 저장된 리프레시 토큰을 즉시 삭제(무효화)하여 재사용을 차단한다.
        3. [시스템]: 예외(`REFRESH_TOKEN_NOT_MATCHES`)를 반환하고 흐름을 종료한다.

### 3.3. [UC-AUTH-03] 로그아웃

1. 기본 정보
    - 목적: 저장된 리프레시 토큰을 폐기하여 재발급을 통한 세션 연장을 차단한다.
    - 행위자: 인가된 사용자
    - 사후 조건: 데이터 상태 변경 없음(Redis 키 삭제) 외에 부수 효과 없음. 클라이언트의 리프레시 토큰 쿠키가 만료 처리된다.

2. 기본 흐름
    1. [행위자]: 인증된 상태에서 로그아웃을 요청한다.
    2. [시스템]: 인증 주체의 유저 식별자로 Redis에 저장된 리프레시 토큰을 삭제한다.
    3. [시스템]: 리프레시 토큰 쿠키를 즉시 만료시켜 응답한다.

3. 대안 흐름
   (이미 만료되었거나 존재하지 않는 토큰을 삭제해도 오류 없이 정상 종료되므로 별도 대안 흐름 없음)

4. 예외 흐름
   (해당 없음)

### 3.4. [UC-USER-01] 회원가입

1. 기본 정보
    - 목적: 신규 사용자의 계정을 생성한다.
    - 행위자: 비인가 사용자
    - 사후 조건: 포인트 0, 권한 `ROLE_USER`로 초기화된 유저가 생성된다.

2. 기본 흐름
    1. [행위자]: 이메일, 비밀번호, 이름, 생년월일, 성별, 전화번호를 포함하여 회원가입을 요청한다.
    2. [시스템]: 요청받은 이메일이 이미 가입되어 있는지 확인한다.
    3. [시스템]: 비밀번호를 암호화한다.
    4. [시스템]: 식별자를 발급하고, 암호화된 비밀번호와 함께 유저 생성 컨텍스트를 구성한다.
    5. [시스템]: 포인트 0, 권한 `ROLE_USER`로 초기화된 유저를 생성한다.
    6. [시스템]: 생성된 유저를 저장하고 유저 식별자를 반환한다.

3. 대안 흐름
   (기본 흐름 외의 정상 대안 흐름 없음)

4. 예외 흐름
    - [E-1] 이메일 중복 (기본 흐름 2번에서 발생)
        1. [시스템]: 요청받은 이메일이 이미 존재함을 확인한다.
        2. [시스템]: 예외(`EMAIL_ALREADY_EXISTS`)를 반환하고 흐름을 종료한다.

### 3.5. [UC-USER-02] 이메일 중복 확인

1. 기본 정보
    - 목적: 회원가입 이전에 이메일 사용 가능 여부를 사전에 확인한다.
    - 행위자: 비인가 사용자
    - 사후 조건: 데이터 상태 변경 없음(Read-only).

2. 기본 흐름
    1. [행위자]: 확인할 이메일을 포함하여 조회를 요청한다.
    2. [시스템]: 해당 이메일이 이미 존재하는지 조회한다.
    3. [시스템]: 사용 가능 여부(존재하지 않으면 `true`)를 반환한다.

3. 대안 흐름 / 예외 흐름
   (해당 없음)

### 3.6. [UC-USER-03] 배송지 추가

1. 기본 정보
    - 목적: 사용자의 배송지를 등록하고 대표 배송지 규칙을 적용한다.
    - 행위자: 인가된 사용자

2. 기본 흐름
    1. [행위자]: 수령인, 연락처, 우편번호, 주소, 상세주소, 대표 지정 여부를 포함하여 배송지 추가를 요청한다.
    2. [시스템]: 요청자 식별자로 유저를 조회한다.
    3. [시스템]: 새 배송지의 식별자를 발급한다.
    4. [시스템]: 요청된 대표 지정 여부, 기존 배송지 존재 여부, 기존 대표 배송지 존재 여부를 종합하여 신규 배송지의 최종 대표 여부를 결정한다.
    5. [시스템]: 신규 배송지가 대표로 결정되고 기존 대표 배송지가 있다면 기존 대표 상태를 해제한다.
    6. [시스템]: 배송지를 생성하여 유저의 배송지 목록에 추가한다.
    7. [시스템]: 변경된 유저를 저장한다.

3. 대안 흐름
   (기본 흐름 4번의 대표 결정 로직 자체가 여러 케이스를 포괄하므로 별도 대안 흐름 없음)

4. 예외 흐름
    - [E-1] 유저 없음 (기본 흐름 2번에서 발생)
        1. [시스템]: 요청자 식별자에 해당하는 유저가 없음을 확인한다.
        2. [시스템]: 예외(`USER_NOT_FOUND`)를 반환하고 흐름을 종료한다.

### 3.7. [UC-USER-04] 배송지 삭제

1. 기본 정보
    - 목적: 사용자의 배송지를 제거하고, 제거 대상이 대표 배송지였을 경우 승계 규칙을 적용한다.
    - 행위자: 인가된 사용자

2. 기본 흐름
    1. [행위자]: 삭제할 배송지 식별자를 포함하여 삭제를 요청한다.
    2. [시스템]: 요청자 식별자로 유저를 조회한다.
    3. [시스템]: 요청한 식별자의 배송지가 유저의 배송지 목록에 존재하는지 확인하고 제거한다.
    4. [시스템]: 제거된 배송지가 대표였고 남은 배송지가 있다면, 남은 배송지 중 첫 번째 배송지를 새로운 대표로 승격한다.
    5. [시스템]: 변경된 유저를 저장한다.

3. 대안 흐름
   (기본 흐름 외의 정상 대안 흐름 없음)

4. 예외 흐름
    - [E-1] 유저 없음 (기본 흐름 2번에서 발생)
        1. [시스템]: 요청자 식별자에 해당하는 유저가 없음을 확인한다.
        2. [시스템]: 예외(`USER_NOT_FOUND`)를 반환하고 흐름을 종료한다.
    - [E-2] 배송지 없음 (기본 흐름 3번에서 발생)
        1. [시스템]: 요청한 식별자의 배송지가 해당 유저 소유 목록에 존재하지 않음을 확인한다.
        2. [시스템]: 예외(`SHIPPING_ADDRESS_NOT_FOUND`)를 반환하고 흐름을 종료한다.
