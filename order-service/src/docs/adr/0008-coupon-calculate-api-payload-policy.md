# ADR-0008: 주문서 생성시 쿠폰 계산 API 페이로드 정책

- **Status:** Accepted
- **Date:** 2026-06-16
- **Author:** 최민식
- **Tags:** #Coupon #Policy 
- 
## 1. Context (배경 및 문제 상황)

주문서 생성시 유저가 선택한 쿠폰들의 최종 할인 금액을 계산하기 위해 쿠폰 서비스의 `POST /internal/coupons/calculate`를 호출해야한다
이때 주문 서비스에서 쿠폰 서비스로 넘겨줄 데이터 페이로드를 설계하여야 한다
## 2. Alternatives (고려했던 대안들)

1. **[대안 1: 쿠폰이 적용된 상품만 필터링 하여 전송한다]**
    - 설명: 사용자가 쿠폰을 사용하기로 선택한 상품의 정보와 상품 쿠폰 아이디 정보만 필터랑 하여 전송한다
    - 장점: 데이터 페이로드가 작아져 페이로드가 최적화 된다
    - 단점: 장바구니 쿠폰의 제약과 할인 금액을 계산하기 위해 다시 주문 서비스를 호출해야하는 역방향 조회가 발생한다
2. **[대안 2: 주문을 요청한 전체 상품 정보를 모두 전송한다]**
    - 설명: 사용자가 주문을 요청한 상품의 정보를 모두 전송한다 (쿠폰 미적용 상품은 `itemCouponId: null` 처리) 
    - 장점: 장바구니 쿠폰 할인 금액을 계산하기 위한 모든 정보가 페이로드에 포함되어 있으므로 쿠폰 서비스에서 추가적인 역방향 조회와 같은 구조가 필요 없게됨
    - 단점: 쿠폰 할인 계산 페이로드가 커짐

## 3. Decision (결정)

- **[대안 2: 주문을 요청한 전체 상품 정보를 모두 전송한다]** 를 선택한다.
- **이유:** 최소 결제금액 충족 여부, 특정 상품 할인 제외 등을 판단하는 책임은 쿠폰 도메인 서비스의 핵심 비지니스 책임임
쿠폰 서비스가 이를 자체적으로 계산하기 위해서는 주문 전체의 컨텍스트가 필요하다
대안 1을 선택할 경우 쿠폰 서비스가 주문 서비스를 다시 조회하는 순환 참조 구조가 발생한다
또한 새로운 형태의 쿠폰이 추가되더라도 주문 서비스는 전체 데이터를 넘겨주는 현재 구조를 수정할 필요가 없다

## 4. Consequences (결과 및 영향)

### 👍 Positive (얻게 된 것)
- 쿠폰 서비스는 외부 상태에 의존하지 않는 형태로 동작하게 되어 테스트 및 스케일 아웃에 용이해짐
- 주문서비스와 쿠폰 서비스의 결합도가 낮아진다

### 👎 Negative (잃은 것 / 감당할 것)
- 쿠폰 미적용 상품 정보까지 직렬화 하여 전송하기 때문에 API 페이로드가 증가한다
