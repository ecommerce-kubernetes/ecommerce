# ADR-0002: SAGA 실패 후 결제 환불 비동기 처리

- **Status:** Accepted
- **Date:** 2026-06-10
- **Author:** 최민식
- **Tags:** #SAGA, #Event, #Payment
- 
## 1. Context (배경 및 문제 상황)

주문 Saga가 실패한 경우 SAGA 롤백이 완료된 이후 승인된 결제를 취소 해주어야 함
결제 기록을 확인하여 결제 취소를 진행해야함 결제 취소는 외부 PG(토스) 의 결제 취소 API 호출이 필요하고 외부 서비스 API 호출이라는걸 고려해야함

해당 로직을 구현할때 고려해야하는 부분은 다음과 같음
1. 결제 취소는 PG 사의 API 를 호출하여 이루어 지고 이는 외부 API 호출임
2. SAGA 실패와 주문 상태 변경은 내부 시스템 상태 변경
3. 결제 취소는 외부 PG 처리 요청

## 2. Alternatives (고려했던 대안들)

1. **대안 1: 주문,SAGA 실패와 결제 취소를 원자적으로 처리**
    - 설명: `OrderSagaManager`가 하나의 트랜잭션으로 주문 상태 변경, SAGA 실패, 결제 취소를 처리함
    - 장점: 주문과 SAGA, 결제 상태 무결성이 유지됨, 주문이 실패되면 SAGA, 결제 상태도 실패 또는 환불 상태이므로 데이터가 일관성이 보장됨
    - 단점: 결제 취소는 외부 PG API 를 요청해야하기 때문에 하나의 트랜잭션으로 원자적으로 처리할 경우 DB 트랜잭션 안에서 외부 API 호출부가 돌아가게 됨
2. **대안 2: 결제 API 호출을 비동기 이벤트로 분리**
    - 설명: `OrderSagaService`가 Saga 실패 처리와 history 저장 후 비동기 이벤트를 발행하여 리스너를 통해 결제 취소 처리를 수행
    - 장점: PG 장애가 내부 DB 트랜잭션으로 전파되는 것을 차단
    - 단점: 결과적 일관성을 맞추기 위한 대사 스케줄러 구현 비용 발생

## 3. Decision (결정)

- **[대안 2: 결제 API 호출을 비동기 이벤트로 분리]** 를 선택
- **이유:** DB 커넥션 내에서 외부 동기 호출을 분리하여 시스템 안정성을 높여야 하고 스케줄러 구현 비용보다 DB 커넥션 풀 부족 문제로 발생하는 문제 해결이 더 치명적임
또한 SAGA 실패와 주문 상태 변경은 서로 연관되어있고 내부 시스템 상태 변경으로 처리가 가능하지만 결제 취소는 외부 PG 사의 결과를 의존하기 때문에 서로 다른 바운더리를 가진다
따라서 결제를 Saga 실패와 주문 상태 변경과 한번에 처리해야하는 이유가 타당하지 않음 

## 4. Consequences (결과 및 영향)

### Positive (얻게 된 것)
- 시스템 장애 격리(Fault Isolation) 달성.
- 주문 로직과 결제 외부 연동 로직의 강결합 해소
- 시스템 안정성 확보 및 DB 커넥션 풀 고갈 문제 해결

### Negative (잃은 것 / 감당할 것)
- 트랜잭션이 분리되므로, 이벤트 유실이나 PG사 에러 발생 시 상태를 복구할 대사 스케줄러 배치가 추가로 개발되어야 함.
- 코드의 실행 흐름이 이벤트를 통해 파편화되므로 시퀀스 다이어그램과 같은 시스템 흐름을 표현하는 기록이 필요함
