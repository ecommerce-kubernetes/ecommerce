# ADR-0004: SAGA 스케줄러 정책 및 양방향 멱등성 도입

- **Status:** Accepted
- **Date:** 2026-06-11
- **Author:** 최민식
- **Tags:** #SAGA, #Scheduler #kafka #Idempotency
-
## 1. Context (배경 및 문제 상황)

Kafka 기반의 비동기 통신 SAGA 오케스트레이션 환경에서는 네트워크 지연, 서버 다운, 메시지 유실 등으로 인해 문제가 발생할 수 있다
따라서 이러한 치명적인 상황에 대한 자동 복구 및 방어 로직이 필요하다

1. **정방향 고아 객체 및 유령 응답:** 재고 차감, 쿠폰 무효화 등 정방향 통신 명령의 무응답으로 인해 SAGA가 보상 처리 되었지만 뒤늦게 성공 메시지가 넘어오는 현상 (지각 메시지)
2. **역방향 고아 객체:** 보상 명령을 보냈으나 대상 서버가 일시적으로 다운되어 응답이 없는 현상
3. **보상 트랜잭션 영구적 실패:** DB 데이터 유실 등 물리적인 원인으로 인해 SAGA 참여 서비스에서 보상 실패 메시지를 발행하여 SAGA 가 멈추는 현상

이러한 예외 상황들을 스케줄러가 어떻게 처리해야 하며 각 서비스는 중복 메시지를 어떻게 방어해야하는지에 대한 명확한 규정이 있어야 한다

## 2. Alternatives (고려했던 대안들)

1. **[대안 1: 스케줄러의 강제 데이터 수정]**
    - 설명: 스케줄러가 SAGA 참여 서비스의 DB를 직접 조회하여 불일치 시 명령을 보내 정합성을 맞춘다
    - 장점: 모든 복구 로직이 스케줄러 한곳으로 중앙 집중화 될 수 있다.
    - 단점: 스케줄러가 모든 도메인 지실을 알게 되고 영구적 장애 발생시에 스케줄러가 해당 데이터를 더 망가트리는 문제가 발생할 수 있음
2. **[대안 2: 스케줄러의 제한적 트리거 및 양방향 멱등성 방어]**
    - 설명: 스케줄러는 SAGA 상태만 보고 명령 재발송을 수행하며 실제 데이터 정합성 방어는 송수신 양쪽 서비스의 멱등성 로직에 위임하는 방식
    - 장점: 스케줄러는 SAGA 보상 처리를 명령 재발송을 통해서 수행하기 때문에 서비스간의 강결합 해소
    - 단점: SAGA 참여 서비스 개발시 멱등성을 보장하기 위한 로직이 강제됨

## 3. Decision (결정)

- **[대안 2: 스케줄러의 제한적 트리거 및 양방향 멱등성 방어]** 를 선택한다.

A. 스케줄러 원칙
1. 정방향 지연(`STARTED` 상태의 SAGA): 임의의 시간 경과시 스케줄러는 **SAGA를 보상 처리 상태로 변경하고 보상 명령을 발행**한다
2. 역방향 지연(`COMPENSATING` 상태의 SAGA + 실패 SAGA 이력이 저장되지 않음): 해당 상황은 보상 처리 명령을 보냈지만 대상 서버가 일시적인 문제로 인해 
보상 명령 수행을 하지 못해 보상 명령 결과 메시지 발행이 지연되고 있는 상황이므로 **대상 서버가 복구 될때 까지 동일한 보상 명령을 반복 발행**한다
3. 영구적 실패(`COMPENSATING` 상태의 SAGA + 실패 SAGA 이력이 존재): 해당 상황은 대상 서버가 보상 명령을 수행하지 못하여 처리 실패 메시지가 발행되어
SAGA 이력에 기록된 상태이다 따라서 **절대 자동 복구를 시도하지 않고 SAGA를 그 상태 그대로 멈춰둔 뒤 개발자가 수동 개입** 한다

B. 양방향 멱등성 강제
1. 오케스트레이터: 유령 응답(지각 응답)을 차단하기 위해 수신된 메시지의 `step`과 현재 SAGA `step`이 다르면 무조건 메시지를 드랍(무시)한다
2. SAGA 참여 서비스: 스케줄러 재시도로 인해 중복 보상 명령이 유입될 경우(역방향 지연시) **보상 명령은 단 한번만 실행하되 메시지가 유실 될 수 있으므로 
성공 응답은 수신한 횟수 만큼 무조건 다시 발행하여야 한다**

C. 오케스트레이터 2중 중복 응답 방어
1. 1차 논리적 방어: 유령 응답이나 중복 응답이 들어올 경우 `handleReply` 진입시 수신한 메시지 `step`과 현재 SAGA의 `step` 이 동일한지 확인후
다르면 메시지를 무시한다
2. 2차 물리적 방어: 동시에 중복 응답이 유입되어 1차 방어가 통과 되더라도 `OrderSagaInstance`의 JPA `@Version` 기반 낙관적 락을 뒤늦은 트랜잭션을
롤백(`OptimisticLockingFailureException`) 시킨다 이후 카프카가 해당 메시지를 재시도 하면 1차 방어 로직으로 무시된다
## 4. Consequences (결과 및 영향)

### Positive (얻게 된 것)
- 데이터 정합성: 네트워크 지연이나 서버 다운이 발생하더라도 데이터가 어긋나지 않는다
- 안전한 장애 격리: 시스템 스스로 복구할 수 없는 장애를 격리하여 개발자에게 문제 해결을 위임함으로써 2차 문제를 방지한다
- 동시성 제어: 오케스트레이터는 별도의 조회 없이 `step` 과 `@Version` 만으로 무결성을 보장한다

### Negative (잃은 것 / 감당할 것)
- SAGA 참여 서비스 개발시 반드시 멱등성 패턴 구현이 강제된다
