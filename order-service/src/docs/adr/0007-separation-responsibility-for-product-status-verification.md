# ADR-0007: 상품 상태 검증 책임 분리 및 범용 조회 API

- **Status:** Accepted
- **Date:** 2026-06-15
- **Author:** 최민식
- **Tags:** #MSA #BoundedContext #OrderValidation, #Coupling

## 1. Context (배경 및 문제 상황)

- 현재 주문서 생성(`initialOrder`) 및 장바구니 담기, 주문 생성 로직에서 상품의 주문 가능 여부(재고 부족, 상품 판매 상태 등)을 상품 서비스(Product Service)가 직접 판단하여 에러
  응답을 반환함으로써 주문 서비스는 상품 서비스의 결과를 통해 비지니스 예외를 발생시키는 구조로 비지니스 로직이 구현되어 있음
- 이 구현을 위해 상품 서비스는 `POST /products/validate-for-order`, `POST /product/validate-for-cart` 처럼 호출자의 명령에 종속된 중복 API이 생성되어야
  함
- 결과적으로 상품 서비스가 "주문" 과 "장바구니" 라는 외부 도메인 비지니스 룰을 알아야 하는 문제(Coupling)이 발생했고 다른 서비스에서 상품 정보를 단순히 조회하고자 할때 API의 재사용성이 떨어지는
  아키텍처 병목이 발생
- 주문 서비스에서 장바구니 추가 또한 수량 검증을 한다고 요구사항이 변경되는 경우 변경된 비지니스 요구사항은 주문 서비스임에도 불구하고 상품 서비스 API를 수정해야하는 도메인 규칙이 누수되는 문제가 발생하게 됨
- 상품 서비스가 현재 상품의 상태와 수량을 반환하는것은 현재 상품의 사실을 반환하는 구조이므로 도메인 누수가 될 수 없음

## 2. Alternatives (고려했던 대안들)

1. **[대안 1: 상품 서비스 내부에서 호출자별(`Order`, `Cart`) 등 검증 API 유지]**
    - 설명: 상품 서비스가 재고 수량과 상태를 확인해 호출자에 따라 에러를 던지는 구조
    - 장점: 주문 서비스의 코드량이 주문 서비스는 단순히 주문 상품을 상품 서비스에 요청하기만 하면 검증까지 수행되는 단순한 구조를 가져갈 수 있음
    - 단점: 상품 도메인에 주문/장바구니 도메인 규칙이 누수되어 새로운 요구사항이 추가될 경우 상품 서비스 코드를 수정해야하는 OCP 위반이 발생
2. **[대안 2: 상품 서비스는 현재 상품의 사실만을 제공하고 해당 데이터에 대한 판단은 호출자로 위임]**
    - 설명: 상품 서비스는 요청받은 상품의 재고량, 판매 상태와 같은 사실만을 반환하고 주문 서비스에서 자신의 비지니스 규칙에 맞춰 주문 가능여부, 장바구니 추가 가능 여부를 직접 검증
    - 장점: 마이크로 서비스간의 역할 분리 및 상품 조회 API 범용성을 극대화 할 수 있다
    - 단점: 주문 서비스 내부에서 해당 상품에 대한 주문 가능 여부 등 추가 검증 로직이 필요함

## 3. Decision (결정)

- **[대안 2: 상품 서비스는 현재 상품의 사실만을 제공하고 해당 데이터에 대한 판단은 호출자로 위임]** 를 선택한다.
- **이유:** 상품이 재고 부족 또는 상태에 따라 주문이 가능한지 불가능한지는 주문 서비스의 고유 비지니스 규칙이다 따라서 상품 서비스는 상품에 대한 사실만을 제공하고 주문서비스가 스스로의 비지니스 규칙에 따라
  통제하도록 하는것이 시스템 확장성에 있어 유리하다 주문 서비스의 요구사항이 변경되더라도 변경된 요구사항에 상품 서비스는 영향을 받지 않고 주문 서비스 로직만을 수정하면 되기 때문에 결합도가 낮아짐

## 4. Consequences (결과 및 영향)

### 👍 Positive (얻게 된 것)

- 재사용성: 상품 서비스는 조회 API가 호출자의 맥락에서 벗어나 범용적인 형태로 가져갈 수 있음
- 응집도: 상품이 주문가능한지, 상품이 장바구니에 추가 가능한지에 대한 정책이 변경되어도 상품 서비스는 수정, 배포될 필요 없이 오직 주문 서비스만 수정하고 배포되면 되기 때문에 응집도 향상
- 장애 격리: 상품 재고 부족시 장바구니 서비스는 에러를 반환하지 않고 장바구니에 추가하거나 품절을 반환, 주문 서비스는 주문을 차단하는 동일한 상황을 안전하게 처리 가능하게 됨

### 👎 Negative (잃은 것 / 감당할 것)

- 주문 서비스에서 상품의 상태를 판단하고 수량을 검증해야하기 때문에 추가 검증 로직 추가가 필요
