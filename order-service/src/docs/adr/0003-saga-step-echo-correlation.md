# ADR-0003: 통합 응답 토픽 환경에서 SagaStep 메아리 패턴을 통한 메시지 식별

- **Status:** Accepted
- **Date:** 2026-06-10
- **Author:** 최민식
- **Tags:** #SAGA, #Kafka, #Correlation
-
## 1. Context (배경 및 문제 상황)

현재 Saga에 참여하는 각 서비스들의 메시지 토픽은 다음과 같음
- `order -> product`: 재고 명령
- `order -> coupon`: 쿠폰 명령
- `order -> user`: 포인트 명령
- `product, coupon, user -> order`: 통합 응답 토픽

각 마이크로 서비스들이 작업을 마치고 통합 응답 토픽으로 `SagaReplyMessage`를 발행할때 오케스트레이터인
`OrderSagaManager`는 해당 응답이 어떤 서비스의 작업에 대한 결과인지 식별해야 다음 SAGA 스텝으로 넘어갈 수 있음
이를 식별하기 위해서 상관관계 키 설계가 필요함.

## 2. Alternatives (고려했던 대안들)

1. **[대안 1: 응답 주체를 명시하는 방식]**
    - 설명: 응답 메시지에 `COUPON-SERVICE`와 같이 메시지를 발행한 도메인 서비스 이름을 적어서 보냄
    - 장점: 메시지 페이로드를 통해 어디서 온 데이터인지 바로 알 수 있음
    - 단점: `OrderSagaManger`가 메시지를 보낸 서비스 이름을 SagaStep(도메인)으로 매핑해야함
2. **[대안 2: SagaStep 페이로드 메아리 방식]**
    - 설명: `OrderService`가 명령을 발행할때 현재 진행중인 `SagaStep` 값을 메시지에 담아 보내면 이를 수신하는 서비스는 이 값이 무엇인지 
            알 필요 없이 응답할때 받았던 `step` 값을 그대로 메아리 처럼 담아 보냄
    - 장점: 각 참여 마이크로 서비스들은 `step` 필드를 그대로 보내면 되기 때문에 주문 서비스와 결합도를 줄일 수 있음
    - 단점: 참여 마이크로 서비스는 자체 로직 수행후 응답 객체를 만들때 `step` 필드를 반드시 입력해야함

## 3. Decision (결정)

- **[대안 2: SagaStep 페이로드 메아리 방식]** 를 채택
- **이유:** `SagaManager`는 발신자의 물리적인 이름이 아니라 **어떤 Step의 작업이 완료되었는지**이다.
            스텝 자체를 주고 받으면 `SagaManager`는 추가적인 매핑 작업 없이 멱등성 검증, 다음 스텝 진행을 수행할 수 있고,
            참여 마이크로 서비스들은 SAGA라는 컨텍스트를 전혀 모른채 독립적으로 작동할 수 있다.

## 4. Consequences (결과 및 영향)

### 👍 Positive (얻게 된 것)
- `SagaManager`는 해당 응답이 어떤 서비스가 보냈는지 매핑할 필요 없이 넘어온 `step`과 현재 `step`의 비교를 통해 지연 메시지나 중복 메시지를 
차단 가능하다
- `User`, `Product`, `Coupon` 서비스는 SAGA의 존재를 몰라도 되고 요청에 들어온 `step`핃르를 응답할때 그대로 복사해서 돌려주면 된다

### 👎 Negative (잃은 것 / 감당할 것)
- 참여자 서비스들은 자체 로직을 수행후 응답 객체를 만들때 반드시 요청으로 들어온 `step` 필드를 누락 없이 바인딩 해야한다
