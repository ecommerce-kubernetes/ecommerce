# ADR-0006: 시간 의존성 격리를 위한 Clock 객체 도입 및 Ioc 적용

- **Status:** Accepted
- **Date:** 2026-06-15
- **Author:** 최민식
- **Tags:** 예: #Clock, #Time Dependency

## 1. Context (배경 및 문제 상황)

- 도메인 및 서비스 로직에서 시스템의 현재 시간 `LocalDateTime.now()`을 직접 호출하는 경우, 코드가 실행되는 환경의 OS 시계에 강하게 결합된다
- 테스트 실행 시점마다 결과가 달라지는 깨지기 쉬운 테스트가 발생할 위험이 높으며 특정 시간에 벌어지는 엣지 케이스를 테스트하기 어렵다
- 서비스 코드 또한 로직을 실행하는 시점 (`validateAccess`)과 도메인이 저장되는 시점(`repository.save()`) 이 미세하게 달라져 데이터 불일치가 발생할 수 있다

## 2. Alternatives (고려했던 대안들)

> *어떤 선택지들이 있었는가?*

1. **[대안 1: 도메인 및 서비스에서 `LocalDateTime.now()` 직접 호출]**
    - 설명: 별도의 의존성 없이 필요한 곳 마다 자바 `LocalDateTime.now()` 호출
    - 장점: 구현이 빠르고 직관적이며 초기 세팅이 필요 없음.
    - 단점: 테스트 환경에서 시간을 고정할 수 없어 깨지기 쉬운 테스트가 발생, 트랜잭션 내부에서 호출 시점마다 시간이 달라져 데이터 정합성이 깨질 위험이 있다
2. **[대안 2: 테스트에서 `Mockito.mockStatic`을 사용해 시간 조작]**
    - 설명: 프로덕션 코드는 `LocalDateTime.now()`을 사용하고 테스트에서만 `mockStatic(LocalDateTime.class)`를 사용하여 테스트를 진행
    - 장점: 프로덕션 코드는 코드 수정이 필요 없음
    - 단점: 테스트 속도 저하, 병렬 테스트시 쓰레드 데드락 발생
3. **[대안 3: `java.time.Clock` 을 사용]**
    - 설명: `java.time.Clock` 객체를 주입받아 사용하며, 비지니스 트랜잭션 진입점에서 한번만 시간을 캡쳐하여 데이터 정합성을 보장
    - 장점: 테스트에서 시간을 고정하여 테스트 할 수 있어 멱등성이 보장되는 테스트 작성 가능
    - 단점: Clock 설정이 강제됨

## 3. Decision (결정)

- 우리는 **[대안 3: `java.time.Clock`을 사용]** 선택
- **이유:** Clock을 사용하여 테스트 시간을 고정해 테스트 하므로 언제나 성공하는 테스트를 작성할 수 있다.
  시간을 조회하는 행위는 외부 인프라(OS 시계)에 의존하는 작업이다 따라서 시간 조회를 도메인에서 밀어내고 파라미터로 주입받도록 설정하여 외부 환경에
  오염되지 않는 형태의 도메인 설계가 가능하다 또한 비지니스 트랜잭션 내에서 단 한번의 시간 캡쳐로 하위 도메인 전체가 해당 시간을 공유하게 설정할 수 있어
  트랜잭션의 정합성을 유지할 수 있다.

## 4. Consequences (결과 및 영향)

### Positive (얻게 된 것)

- 도메인 모델이 시스템 시계로부터 격리되고 순수한 메모리 기반의 비지니스 로직에 집중할 수 있게 됨
- `Clock.fixed()` 를 주입하여 시간을 완벽하게 통제할 수 있으므로 멱등성이 보장되는 테스트 작성 가능

### Negative (잃은 것 / 감당할 것)

- 시간에 의존하는 메서드의 시그니처에 LocalDateTime 파라미터가 추가되어야 한다
- 테스트 컨텍스트 초기화 시 Clock Bean 설정 강제된다
