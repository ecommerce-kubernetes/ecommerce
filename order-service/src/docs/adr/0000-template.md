## 1. Context (배경 및 문제 상황)
> *우리가 왜 지금 이 결정을 내려야만 하는가?*

- 현재 직면한 비즈니스적/기술적 문제 상황을 객관적으로 서술합니다.
- 코드로 해결할 수 없는 병목이나, 장애가 발생했던 이력, 새로운 기획 요구사항 등을 적습니다.
- **예시:** 결제 트래픽 스파이크 시, 외부 PG사(토스페이먼츠)의 응답 지연으로 인해 우리 내부 주문 DB 커넥션 풀이 고갈되는 장애가 간헐적으로 발생하고 있음.

## 2. Alternatives (고려했던 대안들)
> *어떤 선택지들이 있었는가?*

1. **[대안 1: RestTemplate/WebClient 타임아웃 단축]**
    - 설명: RestTemplate를 사용하여 구현함
    - 장점: 구현이 매우 간단함.
    - 단점: 정상적인 결제 지연 건까지 강제로 실패 처리되어 매출 하락 및 고객 클레임 증가 예상.
2. **[대안 2: 외부 API 호출을 비동기 이벤트로 분리]**
    - 설명: 외부 API 호출 이벤트로 구현함
    - 장점: 외부 장애가 내부 DB 트랜잭션으로 전파되는 것을 원천 차단(장애 격리).
    - 단점: 결과적 일관성을 맞추기 위한 대사 스케줄러(Reconciliation) 구현 비용 발생.

## 3. Decision (결정)
> *그래서 최종적으로 무엇을 선택했고, 그 이유는 무엇인가?*

- 우리는 **[대안 2: 외부 API 호출을 비동기 이벤트로 분리]**를 선택한다.
- **이유:** 시스템의 안정성(DB 커넥션 보호)이 단기적인 개발 비용(스케줄러 구현)보다 압도적으로 중요하며, 향후 결제 도메인을 별도의 마이크로서비스로 분리할 때를 대비하여 결합도를 낮춰야 하기 때문이다.

## 4. Consequences (결과 및 영향)
> *이 결정으로 인해 우리가 감당해야 할 트레이드오프는 무엇인가?*

### 👍 Positive (얻게 된 것)
- 시스템 장애 격리(Fault Isolation) 달성.
- 주문 로직과 결제 외부 연동 로직의 강결합 해소 (OCP 충족).

### 👎 Negative (잃은 것 / 감당할 것)
- 트랜잭션이 분리되므로, 이벤트 유실이나 PG사 에러 발생 시 상태를 복구할 대사 스케줄러 배치가 **반드시** 추가로 개발되어야 함.
- 코드의 실행 흐름(Flow)이 이벤트를 통해 파편화되므로, 신규 입사자를 위한 시퀀스 다이어그램 업데이트가 필요함.
