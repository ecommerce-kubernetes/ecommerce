# ADR-0001: SAGA 종료시 주문 상태 동기 및 원자적 처리 

- **Status:** Accepted
- **Date:** 2026-06-10
- **Author:** 최민식
- **Tags:** #SAGA, #Transaction, #Order
-
## 1. Context (배경 및 문제 상황)

주문 Saga 오케스트레이터를 구현하는 과정에서 최종 완료 및 실패 후 주문 상태를 변경해야함
기존 구조에서는 `OrderSagaService`에서 Saga 인스턴스 및 history를 저장한 뒤 이벤트를 발행하고 이벤트 리스너가 수신하여 주문의 상태를 변경하는 구조로 
설계되었음

기존에 구현된 방식으로 처리했을 경우 다음과 같은 문제 상황이 발생할 수 있음을 확인하였음
1. **데이터 불일치**: 이벤트를 통해 주문 상태 변경과 Saga 인스턴스 상태 변경, history 저장 처리 트랜잭션을 분리하면 Saga 인스턴스는 Complete 인데 
 주문은 여전히 PAID 상태인 데이터 불일치 상태가 발생

2. **중복 호출**: 메인 트랜잭션과 비동기 리스너 간의 실행 타이밍 경쟁으로 인해 도메인 내부 검증 로직에서 예외가 발생거나 로그가 찍히는것을 확인하였음

## 2. Alternatives (고려했던 대안들)

1. **대안 1: 기존 구조 유지**
    - 설명: `OrderSagaManager`에서 주문 상태 변경 처리를 하는것이 아니라 `OrderSagaService` 로직 수행 후 이벤트 발행으로 주문 상태를 변경한다
    - 장점: 주문과 saga의 결합도가 낮아진다
    - 단점: 같은 데이터베이스를 사용함에도 결과적 일관성에 의존해야 하기 때문에 데이터 불일치 건을 잡아내기 힘들다
2. **대안 2: OrderSagaManager에서 원자적으로 처리한다**
    - 설명: `OrderSagaManager`에서 `@Transactional`을 사용해 주문 상태 변경과 Saga 인스턴스 상태 변경 및 history 저장을 하나의 트랜잭션으로 
            원자적으로 수행한다
    - 장점: 주문 상태와 Saga 인스턴스 상태, history가 원자적으로 처리되어 불일치 데이터가 만들어지지 않는
    - 단점: `SagaManager`가 주문 서비스와 Saga 서비스 둘다 의존하게 된다

## 3. Decision (결정)
- **[대안 2: OrderSagaManager에서 원자적으로 처리한다]** 를 선택
- **이유:** 동일 데이터베이스내의 데이터는 원자적으로 묶어 일관성을 보장해야하기 때문, 또한 이미 `SagaManager`는 Saga 시작 시점에 주문 정보를 조회하기 위해
            주문 서비스의 의존하기 때문에 대안1 번의 장점은 얻어갈 수 없다

## 4. Consequences (결과 및 영향)
### Positive (얻게 된 것)
- 동일 데이터베이스 내의 논리적 무결성이 유지된다 
- 주문이 PAID인데 Saga 인스턴스 상태는 COMPLETE 또는 FAIL인 데이터가 존재할 수 없기 때문에 불일치 복구 로직이 간단해짐
- 
### Negative (잃은 것 / 감당할 것)
- `OrderSagaManager`는 두개의 도메인에 의존하게 되지만 오케스트레이터의 책임으로 정의
